01 / Problem

音频能听，
却没法逐个音符地改。

学乐器的人想扒谱、练习或重新编曲时，手里通常只有一首混好的歌。把它拆成乐器分轨的音符，目前主要靠人工反复听写，耗时且门槛高。

如何让用户从一首歌出发，更快得到可以试听、修改、继续创作的乐器音轨？

关键不只是能导出文件，还要看音高、节奏和乐器归属是否足够接近原曲，用户改起来是否比从零扒谱更省时间。

难点 01 · 分离

声音混在一起

人声和多种乐器同时发声，频率互相遮挡，容易漏音，也容易把音符分错到别的乐器轨上。

难点 02 · 识别

每种乐器难点不同

钢琴有密集和弦，贝斯音低、起音含糊，鼓要分清底鼓、军鼓、镲片等不同鼓件。

难点 03 · 验证

能导出不等于能用

要逐轨和参考 MIDI 对比，量化漏音、多余音和八度错误，才知道结果有没有使用价值。

02 / Requirements

先验证转写质量，
再决定做多少产品。

调研灵谱（Lingpu）、Audiojam 等竞品。以灵谱为例，它提供多轨展示、音视频转录、逐音编辑，以及 MID / WAV 分别导出，说明用户真正要的是“转完还能改”。据此编写 PRD，暂缓前端，先回答模型能不能转准。

目标用户

学乐器、扒谱、翻弹和编曲的人

输入一首现成歌曲，希望拿到能在音乐软件里继续编辑的分轨音符。

乐器范围

六类目标，MVP 先承诺三轨

MVP钢琴、贝斯、鼓 研究中木吉他、电吉他、弦乐；人声不输出。依据是逐轨实测：三类研究轨的 F1 都低于 10%。

输出规格

Type 1 多轨 MIDI + 处理报告

每类乐器一条轨，写入对应乐器编号；报告记录模型版本、耗时、缺轨和异常原因，方便追溯。

异常处理

先校验，失败要说清楚

检查格式、时长和解码结果；某类乐器没识别出音符就不输出空轨，并在报告里注明原因。

验收原则

逐轨报告指标，不提前宣布达标

指标为音符级 F1（音高一致、起音误差 ≤ 50 ms），并结合试听和人工修改时间综合判断。

03 / Solution

不追求一个模型解决所有问题。

没有从零训练，而是按乐器挑选现有的开源模型与商业工具做对照，再组合使用。每次替换都用同一份参考逐轨比较，确认确实变好了才采用。原型借助 AI 编程工具在本地完成。

01

输入与预处理

校验格式与时长，统一解码，固定时间线。

02

音源分离

先从混音里提取目标乐器，减少其他声音干扰。

03

音符识别

按乐器选用专门的转写模型或多乐器模型。

04

纠错处理

合并重复切分、修正起音、多模型共识补漏音。

05

MIDI 导出

合并为多轨 MIDI，附处理报告，逐轨回测。

钢琴

先分离，再用钢琴专用模型

BS-RoFormer SW 分离出钢琴 → Transkun 转写。在真实钢琴录音上优于整曲转写的基线。

贝斯 · 鼓

换用多乐器模型重新验证

贝斯和鼓替换为 MuScriptor Medium 的输出，与原方案用同一参考对比。权重仅限非商业使用。

吉他 · 弦乐

保留为研究轨道

照常输出，但不计入 MVP 验收；漏音和误报仍然明显，需要更多数据与模型尝试。

04 / Iteration

先找到错在哪，
再决定改什么。

逐轨、逐音对照参考 MIDI，把错误拆成漏音、重复切分和八度错误几类，每一步只针对一类问题改，保留无效方案的负面结果。

结论

钢琴路线在真实录音上成立

5 首全部提升；但遇到电钢、羽管键琴等合成键盘会多报音，产品上应只对原声钢琴启用。

发现

数据集标注差了一个八度

两条路线的贝斯分数都接近 0。对音频测音高后发现，Slakh 贝斯标注比实际发声高一个八度，修正后才得到可信分数。

边界

不把单曲提升当成泛化

BabySlakh 可能在基线的训练数据里，基线有主场优势。贝斯和鼓需要用真实录音多轨数据再复核。

06 / Verification & Versioning

每个结论，都要经得起别人复查。

每个候选版本先冻结成 Git 提交，再交给一个独立 Agent 只读复核。复核者不改文件，也不默认作者的结论是对的；发现问题就修复、再冻结、再复验。

1

冻结版本

提交代码与结果，记录提交号和结果文件哈希。

2

独立复核

另一个 Agent 只读检查评分逻辑、输出文件和边界情况。

3

修复问题

逐条判断复核意见，确认成立的就修复。

4

复验后发布

只复查改动部分，通过后合并、打标签、上线。

复核发现的典型问题：报告把“训练数据可能重叠”写成了确定事实；续跑脚本可能把中途中断的结果当成已完成。两项都已修正。

07 / Takeaways

把“能生成”，
变成“能判断、能改进”。

这个项目最大的收获，是建立了一套能定位问题、能量化改进、也能说清边界的工作方式。

GitHubgithub.com/Max-Ren0/audio-to-midi-mvp 作品集max-ren0.github.io/audio-to-midi-mvp

按音轨定位问题，而不是只看整体分数

不同乐器的错误类型不同，逐轨、逐音的指标才能指导下一步改什么。

用数据收窄范围

六类乐器全做会拖慢验证，所以按实测把 MVP 收到效果最好的三轨，研究轨照常输出但不计入验收。

评测本身也要被检验

标注错误、训练数据重叠、反复调参的开发片段，都会让分数失真。先确认评测可信，再相信结论。

分清技术可行与商业落地

MuScriptor 权重只允许非商业使用，产品化前需要另行解决授权。

下一步
  • 用不在训练集里的真实录音多轨数据，复核贝斯和鼓。
  • 把各轨路线接成任意歌曲一键生成的完整流程，并做端到端评测。
  • 邀请目标用户试听和修改，记录修改时间，再决定前端编辑功能。
