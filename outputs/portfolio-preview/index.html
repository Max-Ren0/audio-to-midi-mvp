01 / THE CHALLENGE

一首歌里，
藏着很多条看不见的轨道。

对想练习、扒谱或重新编曲的人来说，音频方便聆听，却不能直接像 MIDI 一样逐个音符地编辑。项目从这个缺口出发，探索从混合音频生成可编辑乐器轨道的可行性。

如何让用户从一首歌出发，更快获得可以试听、修改和继续创作的乐器音轨？

关键不仅是生成文件，还要判断音高、节奏与乐器归属是否足够接近参考。

01 / INPUT

声音混在一起

人声与多种乐器同时出现，频率相互遮挡，容易出现漏音和串轨。

02 / TRANSCRIPTION

每种乐器难点不同

钢琴有和弦，贝斯强调低音与起音，鼓需要区分不同鼓件。

03 / VALIDATION

能导出不代表能用

需要逐轨对比参考 MIDI，结合漏音、多余音与试听判断实际价值。

MY ROLE / 产品推进

从明确问题，
到用结果做选择。

围绕音频转多轨 MIDI 的可行性，推动需求定义、竞品观察、评测和方案取舍。

需求与范围

先验证核心功能

明确优先处理音频到 MIDI，暂不建设前端；确定钢琴、两类吉他、贝斯、鼓和弦乐六轨，忽略人声。

评测与决策

提供参考并逐轨比较

提供测试音频和参考 MIDI，针对不同音轨要求对比评估，并决定固定钢琴 B 路线。

模型选择

基于实测调整方案

结合 NeuralNote 对照结果，决定将贝斯与鼓切换为 MuScriptor，继续用相同参考评估。

03 / KEY DECISIONS

不追求一个模型
解决所有问题。

围绕每条音轨的表现选择路线，同时保留可对照的实验结果。模型方案是研究选择，不代表所有歌曲的最终效果。

PIANO / 钢琴

先分离，再使用钢琴专用模型

固定 BS-RoFormer SW → Transkun 路线。先从混音中提取钢琴，再识别音符。

BASS & DRUMS

用多乐器模型重新验证两轨

将贝斯和鼓替换为 MuScriptor Medium 的输出，与原 Noto 方案使用同一参考口径比较。

GUITAR / 吉他

分别观察木吉他与电吉他

用分离后的吉他音频或原混音进行转谱；当前两轨仍存在明显漏音和误报。

STRINGS / 弦乐

从剩余声音寻找弦乐

使用 SW 的剩余音轨与 YourMT3，再筛选弦乐；该路线仍需要进一步改善。

05 / MODEL REFLECTION

通用 AI 的能力，
需要适配具体任务。

项目让我认识到，行业需求不同，输入数据、输出形式和衡量标准也会不同。能理解语言的模型，并不必然适合直接识别多乐器音符；音乐转谱还需要处理音高、时值和乐器归属。

方案选择

用现有模型解决专业问题

当前没有从零训练音乐模型，而是选择已有的声音分离、钢琴转谱和多乐器模型，按音轨组合，并通过统一参考比较结果。

项目边界

先完成可验证的小范围实验

受项目阶段和对话 Token 预算影响，暂未进行大规模模型替换与多歌曲验证。本地音乐模型推理还受到运行时间和计算资源限制。

下一步探索

从组合走向数据与模型优化

木吉他、弦乐等轨道仍有明显差距。下一步需要音乐专业人士参与，标注并校对不同乐器的音高、起止时间等数据；在数据、算力和许可允许时，探索模型微调并用新歌曲验证。项目目前尚未完成微调。

06 / TAKEAWAYS

把“能生成”变成
“能判断、能改进”。

项目通过逐轨对照定位问题，并围绕模型效果、数据边界和后续验证持续迭代。

  • 按音轨定位问题，而不是只看整体分数不同乐器的错误类型不同，逐轨指标更能指导选择。
  • 把用户体验放回完整链路从上传、生成到试听、修改和导出，准确率与修正效率共同决定价值。
  • 优先补齐多歌曲验证与可运行流程当前贝斯与鼓替换仍需先准备同源基线；尚非任意歌曲一键生成的成品。
  • 分清技术可行与商业落地本次 MuScriptor 权重标注为非商业使用，未来产品化需另行处理授权。
