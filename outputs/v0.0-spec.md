# v0.0 实现规格（修订版，待审阅）

## 1. 目标与成功定义

输入一个本地 MP3 文件，实际音频长度不超过 180 秒，输出一个 Type 1 标准 MIDI 文件，内含按乐器类别拆分的音轨。用户用现有音乐软件打开并编辑音符。

成功定义分两层：
- 工程层：产物可被重新解析，时间线一致，可在音乐软件中作为多轨打开。
- 音乐层：在评测集上达到第 9 节定义的可用标准。文件能生成不等于识别成功。

不做：前端、网页编辑、试听界面、账号、收费、视频处理、原生 DAW 工程格式、模型训练。

## 2. 输入约束

- 格式：仅接受 MP3。通过解码器确认可解码，并读取实际时长。
- 长度：实际时长超过 180 秒则拒绝，并报告实际长度，不自动截断。
- 采样率：统一重采样到所选模型要求的采样率，具体值在 spike 后确定。
- 非 MP3、损坏或无法解码：拒绝并说明原因。

## 3. 输出约束（MIDI）

- 格式：Type 1，PPQ 固定为 480。
- 节拍：默认 120 BPM、4/4 拍。若 tempo 估计成功，则写入估计值并在日志中注明“估计，可能不准”；估计失败时使用默认值并给出警告。
- 轨道：每个有有效音符的类别生成一条轨道，轨道名为类别名。无有效音符的类别不生成轨道，并在运行日志中列出。
- 通道：鼓使用 channel 10（索引 9），其余类别依次分配其他通道，避免占用 10。
- 力度：默认固定为 80。仅当模型确实输出力度时才写入实际值，不把力度列为能力。
- 时间：所有轨道共用同一时间基准，不做节拍量化。
- MIDI 只保存音符与演奏信息，不保存原始人声、音色、插件和效果器。

## 4. 七类目标与映射规则

七类是识别目标，不代表每首歌都会生成七条有内容的轨道。

| 类别 | 映射依据 | MIDI 通道/程序 | 备注 |
|---|---|---|---|
| 钢琴 | GM program 0–7 | 按分配 | 键盘类统一归入钢琴 |
| 木吉他 | GM program 24–25（尼龙弦、钢弦） | 按分配 | 与电吉他区分不稳定，见下 |
| 电吉他 | GM program 26–31 | 按分配 | 同上 |
| 贝斯 | GM program 32–39 | 按分配 | |
| 鼓 | 打击乐通道（channel 10） | channel 10 | 使用打击乐映射，不按音高归类 |
| 弦乐 | GM program 40–45、48–51 | 按分配 | 排除 46（竖琴）与 47（定音鼓） |
| 人声旋律 | 需在 spike 中确认模型是否支持人声转写 | 按分配 | 未验证前不计入七类完成 |

规则：
- 映射以模型输出的程序编号为准，不以音色判断。
- 不在上表内的输出（如竖琴、定音鼓、合成器音色）不强行归入任一类别，直接丢弃并计入日志。
- 相同类别的多个演奏者首版合并为一条轨道，不承诺逐人拆分。
- 人声只转换唱出的音符，不包含歌词或原唱音色。
- 若 spike 显示木吉他与电吉他无法可靠区分，可将二者合并为“吉他”作为 v0.0 的范围调整，但需用户确认后才能执行。

## 5. 片段整理

长音频分窗处理，窗口与重叠参数在 spike 后校准，初始值如下：
- 窗口长度：30 秒。
- 重叠长度：5 秒。
- 归属规则：每个窗口只保留 onset 落在其中心有效区间内的音符；首尾窗口保留边界内全部音符。

重复判定：同类别、同音高、onset 时间差不超过 50 毫秒视为重复，保留时长较长者。

配对规则：
- note-on 与 note-off 按（类别、音高、通道）配对。
- 未闭合的音符，offset 取 onset 加 10 秒与片段末尾两者的较小值。
- 同音高音符重叠时，截断前一个音符。
- 时长短于 30 毫秒或为负的音符丢弃。

## 6. 技术路线与验证顺序

1. 第一步：时间盒 spike（1 至 2 天，1 首歌）。直接评估多乐器转谱模型（如 MT3 类模型，作为已有研究基线）。确认七类覆盖、依赖能否运行、权重与代码的许可证、单首耗时与内存，并输出一份 MIDI 按第 9 节指标打分。
2. 第二步：若直接路线效果不足，比较“音频分离 + 专用转谱”组合。
3. 若仍无法可靠区分木吉他、电吉他或弦乐，报告未达标并与用户讨论范围，不得自行缩减为两轨后宣称完成。

约束：
- 第一版不训练模型。
- 模型依赖放入独立环境，不改动用户现有 Python 环境。
- spike 结果确定具体模型与版本之前，不声称七类能力已实现。

## 7. 资源与超时

- 机器：spike 阶段记录所用机器（CPU 或 GPU、内存、系统）。正式实现的目标机器在 spike 后确定。
- 耗时上限：单首歌总耗时不超过音频时长的 3 倍（即 180 秒音频最长约 9 分钟）。超过则中止，报告超时。
- 内存上限：峰值内存以 spike 实测值加 30% 余量设定，并在规格中回填具体数字。
- 重试：同一步骤失败最多重试 1 次，不无限重跑。
- 内存不足时，缩短推理块长度后重试一次；仍失败则退出并报告。

## 8. 异常与边界

- 非 MP3、损坏或无法解码：拒绝并说明原因。
- 超过 180 秒：拒绝并说明实际长度。
- 静音、纯讲话或无可靠音符：明确报告无有效转谱结果，不生成空文件宣称成功。
- 部分类别识别失败：输出已识别部分，并说明哪些类别无结果。未识别不代表原曲一定不存在该乐器。
- 低质量录音、串音、重叠声部：给出“结果可能不准确”的提示，不承诺还原原曲。
- 超时或内存不足：按第 7 节处理，不输出半成品冒充完整结果。
- 已有同名输出：默认拒绝覆盖，需显式指定覆盖选项。

## 9. 评测标准

### 9.1 评测数据

- 合成集：用已知 MIDI 配固定 soundfont 渲染得到音频。音频过于干净，仅用于检查类别映射、时间线与格式正确性，不作为音乐质量的依据。
- 真实集：5 至 10 首真实歌曲，人工标注 onset、音高与类别。记录标注人与标注耗时。
- 每首样本需注明包含哪些类别。某类别在样本中不存在时，不计入该类别的分数。

### 9.2 指标

- 主指标：note-level F1，onset 容差 ±50 毫秒，音高一致，类别一致，按类别分别计算。
- 辅助指标：仅 onset 的 F1；onset 误差中位数；各类别的多余音符数与漏音数。
- 每类别需至少 5 首含该类别的样本才给出结论，否则只报告数据，不给出判定。

### 9.3 判定档位（初始提议，待用户确认）

- 可用：该类别 F1 ≥ 0.70。
- 草稿：0.40 ≤ F1 < 0.70，需人工修改后使用。
- 未达标：F1 < 0.40，该类别不作为完成项。

### 9.4 人工工作量

在真实集上记录人工修正 MIDI 所花的分钟数，作为价值指标。

## 10. 验收

1. 文件：产物能被重新解析，并在用户选定的音乐软件中作为多轨打开和编辑。
2. 时间：各轨位于同一时间线；片段接缝处没有明显重复或截断；所有音符起止有效且不为负。
3. 分轨：按第 9 节，对每个有样本支撑的类别给出 F1 与判定档位。缺少该类别的样本不能证明该类识别成功。
4. 价值：记录真实集的人工修改工作量。
5. 运行：记录模型版本、机器、耗时与峰值内存。

## 11. 待用户确认的决策

1. 七类是否确认，尤其是木吉他与电吉他是否允许合并，以及人声旋律是否必须进入 v0.0。
2. 第 9.3 节的判定阈值。
3. 目标机器与资源条件（CPU / GPU、内存上限）。
4. 真实评测集的来源与标注责任人。

## 13. 版本维护与 GitHub 同步

### 13.1 仓库与保存范围

- 使用已建立的私有仓库：`https://github.com/Max-Ren0/audio-to-midi-mvp`。
- 项目代码、规格文档、依赖版本配置、测试、评测方法和版本记录纳入 Git 管理。
- 原始音视频、未经授权的评测素材、模型权重、密钥、本地环境及大量生成结果不上传；通过 `.gitignore` 排除。
- 本规格及后续修订应保存到仓库中；桌面副本与仓库副本发生差异时，先检查差异再同步，不自动覆盖任一方。

### 13.2 自动维护流程

用户授权在推进本项目时，对每个可用版本执行以下流程，无需逐次确认常规提交和上传：

1. 开始修改代码前，检查当前改动，为属于本项目的已有改动创建快照提交；若没有改动，记录现有提交作为恢复点，不创建无意义的空提交。
2. 完成一个可用阶段后，运行与该阶段相关的检查。文档版检查内容与一致性；功能版检查运行结果与相关测试。
3. 检查待上传文件，确认没有密钥、原始媒体或不属于本次工作的改动。
4. 更新 `CHANGELOG.md` 和 `CONTEXT.md`，记录变更、验证结果、已知限制与下一步。
5. 创建说明清楚的提交并推送到 GitHub。重要里程碑另加版本标签，并推送标签。
6. 核对本地与远端的提交编号；只有一致时才报告同步成功。

这里的“自动”指 agent 在执行项目任务时维护版本，不表示聊天停止后仍在后台监控文件。可用版本指完成一项明确工作并经过相应检查的阶段，不要求每次保存文件都上传。

### 13.3 版本号与阶段状态

- 每次提交保存一次可追溯的改动；版本标签标记重要里程碑。
- 使用 `v主版本.次版本.修订版本`，例如 `v0.0.1`。兼容的问题修复增加修订号，新增能力增加次版本号，不兼容的重大变化增加主版本号。
- 规划文档使用预发布标签，例如现有的 `v0.0.0-planning`；实验阶段可使用 `v0.0.0-spike.1`，候选验收版可使用 `v0.0.0-rc.1`。
- `v0.0.0` 作为本规格定义的首个 MVP 验收版本，仅在通过第 10 节验收、且第 11 节相关决策明确后创建。
- 文件可生成、实验可运行、音乐质量达标必须分别记录；不得用版本号暗示尚未验证的能力已经完成。
- 已发布的标签不移动、不覆盖。同一版本需要修正时，新增提交并分配新版本号。

### 13.4 分支、验证与回退

- `main` 保存经过相应检查的阶段成果。较大的模型实验或功能改动使用独立分支，完成检查后再合入。
- 实验失败也应保留必要的代码与结论，但留在实验分支，并标明失败原因，不作为通过验收的版本。
- 每个重要功能版本记录：提交编号、模型及权重标识、依赖版本、关键参数、运行机器、评测集标识、耗时、峰值内存、评测结果和已知限制。缺失项如实注明。
- 需要撤回已上传的改动时，优先通过新增撤销提交恢复；需要复查旧版本时，按标签在独立分支恢复。不强制推送、不删除已发布历史，不覆盖当前未保存工作。
- GitHub 上传失败时保留本地提交，明确报告“本地已保存、远端未同步”，后续恢复上传，不将失败报告为成功。

### 13.5 版本交付记录

每个重要版本交付时提供：版本号或提交编号、仓库链接、本次改动、验证结果、未完成事项与已知风险。规划版和实验版必须明确标注阶段，不能作为 MVP 验收完成的依据。
